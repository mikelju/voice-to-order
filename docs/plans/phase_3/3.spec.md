# Spec Phase 3: FastAPI backend (full pipeline in demo mode)

> Functional specification — WHAT to build and WHY.
> Acceptance criteria are verified with `/7-verify` at the end of the phase.
> Method note: this spec is **derived** from the production system (mapped in full before
> writing it); design decisions port the original, deviations are stated explicitly.

## Problem and goal

**Problem**: the repo has the data (Phase 1) and the search engine (Phase 2) but no
application: the 7-step pipeline described in the case study cannot be run or read as code.

**Goal**: `uvicorn src.backend.app.main:app` starts the API and the complete flow
(process-audio → search-articles → finalize → send) runs end-to-end **locally with no API
keys** (`APP_MODE=demo`), reproducing the original's behavior: same endpoints, same
contracts, same constants, same failure semantics.

## User stories

### US-1: Process a dictated order (demo replay)
**As** a repo user without API keys, **I want** `POST /api/v1/orders/process-audio` to return
a transcription and the extracted order lines, **so that** I can run the real flow with real
(anonymized) recorded orders.

**Acceptance criteria:**
- [x] In demo mode the endpoint replays one of the 47 recorded pairs (`data/extraction_pairs.jsonl`):
      deterministic selection by `recording_id` form field; without it, by hash of the upload bytes
- [x] `GET /api/v1/demo/recordings` lists the recorded orders (id + transcription + n_items)
      so a UI can offer a picker; available only in demo mode (404 in real mode)
- [x] Response contract identical to the original `ProcessAudioResponse` (fields, accents:
      `df_order_json` rows use `CANTIDAD`/`ARTÍCULO`/`DESCRIPCIÓN`)
- [x] The extraction retry x3 with 2s·attempt backoff exists in the real-mode code path and is
      unit-tested with a fake LLM (demo replay does not need it)
- [x] `num_order` is normalized to digits only (`re.sub(r'\D','')`); the simulated ERP enriches
      `planta_name` exactly like the original (success → name, not_found/error → warning)

### US-2: Per-article parallel search (real, against the local DB)
**As** a repo user, **I want** `POST /api/v1/orders/search-articles` to fan out one task per
line under the two named semaphores and return ranked candidates, **so that** the signature
concurrency design of the original is demonstrable and testable locally.

**Acceptance criteria:**
- [x] One asyncio task per article via `asyncio.gather(..., return_exceptions=True)`; a failing
      article is logged and dropped, the rest of the order survives (tested)
- [x] Two semaphores bound the fan-out: LLM=10, DB=10 (named constants)
- [x] Memory-first: `buscar_historicos` (threshold 0.75, count 1) with the hit re-validated
      against the live catalog (`is_active=TRUE`, live description); then `buscar_articulos`
      (threshold 0.5, top 25) deduped against the memory hit; `Date_score`=1/0 and
      `Historical_match` flag exactly as the original
- [x] Query embeddings in demo mode come from the precomputed store (Phase 4 fills it); a query
      without a precomputed vector falls back to **pg_trgm** similarity so demo never errors
      (fallback flagged in logs); in real mode embeddings are computed live
- [x] Re-ranking: in demo mode the **deterministic fallback** of the original — sort by
      (`Historical_match` desc, `Score` desc) — is the ranking (decision: there are no recorded
      re-rank replays; the fallback IS original behavior worth demonstrating). In real mode the
      LLM re-ranker runs with the original prompt and falls back deterministically on any failure
- [x] HNSW warmup is fired (fire-and-forget) when an order starts processing

### US-3: Finalize and deliver on three independent channels
**As** a repo user, **I want** `POST /orders/finalize` + `POST /orders/send` to produce a PDF
and report per-channel status lights, **so that** the isolated-failure delivery design is
visible and chaos-testable.

**Acceptance criteria:**
- [x] `finalize` validates selections exactly like the original (quantity > 0, issues list)
- [x] `send` runs 3 channels with the original semantics: PDF impossible → abort
      (`order_sent_status="fallido"`, everything else `no_intentado`); email (simulated) failure
      → warning only; ERP (simulated) failure → global `fallido`; history failure → warning.
      `error_details` joined with `" | "` using the original literal prefixes
- [x] PDF is real (reportlab): header, Fecha/Usuario/Num Parte/Planta/Plazo fields, checkboxes
      Enviar a Obra / Sólo imputar, observaciones, article table (no supplier column — that
      column was dropped from the public dataset), returned as base64 in `pdf_download_data`
- [x] Email channel is **simulated**: writes the message (recipients chosen with the original
      workday-cutoff-14h rule, retry x3 on simulated connection errors) to `.tmp/outbox/`
- [x] ERP channel is **simulated**: `get_client_data_by_order_id` returns deterministic plant
      names (some ids yield not_found to exercise warnings); `send_order_to_erp` writes the
      original's exact payload shape (`{"IdParte": int, "Lineas": [{"IdArticulo", "Cantidad"}]}`)
      to `.tmp/erp/`; items with Ids `HERRAMIENTA`/`OBSERVACION` are excluded; empty num_order →
      `omitido`
- [x] `SIMULATE_FAILURE=erp,email,history` (substring semantics, like the original) injects
      failures per channel; chaos-tested
- [x] Learned memory upsert on confirmation: `(user_text, catalog_description)` ON CONFLICT
      `frequency+1` + `last_used_month`; new rows get a live embedding in real mode, and in demo
      mode are reachable via the trigram fallback (documented limitation). Decision (deviation
      from the original): the upsert runs in **both** modes — the learning loop is part of what
      this repo demonstrates (the original gated it to `ENVIRONMENT=production`)

### US-4: Manual catalog search
**As** a reviewer, **I want** `GET /api/v1/catalog/search?query=`, **so that** the manual-add
step of the review UI works.

**Acceptance criteria:**
- [x] min 3 chars; AND of `ILIKE %term%` per word over `articulo`; limit 50; same response
      shape (`[{id_articulo, articulo}]`); no `is_active` filter (ported as-is)

## Data contracts

Endpoints, request/response models and field names (including accented field names
`Descripción`/`Artículo`/`ARTÍCULO`/`DESCRIPCIÓN`/`CANTIDAD`) are ported 1:1 from the original
(`ProcessAudioResponse`, `SearchArticlesRequest/Response`, `SearchedArticleItem`,
`FinalizeOrderRequest/Response`, `SendOrderRequest/Response`, `CatalogItem`) — reference:
`.tmp/original-map/backend-pipeline.md` §Contracts. Differences:

- **No JWT auth** (anti-goal: single-user local demo; the original used Supabase Auth)
- New: `GET /api/v1/demo/recordings` → `[{recording_id: int, transcription: str, n_items: int}]`
- New (demo): optional `recording_id` form field in `process-audio`
- `GET /` → `{"message": "... v1. Mode: demo|real"}`

### DB additions (this phase)

| Object | Purpose |
|--------|---------|
| `query_embeddings(query_text text PK, embedding vector(256))` | precomputed demo query vectors (filled in Phase 4) |
| `UNIQUE (user_text, catalog_description)` on `historico_pedidos` | required by the ported upsert |
| function `upsert_historico_with_status(...) → (historico_id, is_new)` | ported verbatim, adapted to the replica's `last_used_month` column |

**Invariants:**
- Search constants are named and equal to the original: semaphores 10/10, thresholds 0.75/0.5,
  top 25, CTE ×3, retry ×3 backoff 2s·attempt, workday cutoff 14h
- `buscar_articulos` / `buscar_historicos` are called as-is (no SQL changes)

## Constraints / decisions

- Python 3.12+ / FastAPI / async end-to-end; **psycopg3 async pool** replaces the Supabase
  client (plain local Postgres); no blocking calls on the event loop — the original's
  `embed_query` sync-inside-async gotcha is fixed (documented deviation)
- `APP_MODE=demo|real` selects providers inside the same services (the original selects LLM
  provider by model-name prefix; that wrapper is ported for real mode)
- LLM prompts ported literally with the real client name in the few-shot examples replaced by
  `[customer]` (anonymization rule)
- New backend dependencies (recorded as the Phase-3 dependency decision, authorized by the
  author): `fastapi`, `uvicorn[standard]`, `pydantic-settings`, `python-multipart`,
  `python-dotenv`, `reportlab`, `httpx` (tests), `pytest-asyncio` (tests), `openai` +
  `google-genai` (real mode, Phase 6 activates them)
- No pandas: the original's DataFrame sort/group is replicated with plain `sorted()`
- Logging ASCII-safe (`[OK]`, `->`), JSON formatter ported, level configurable via `LOG_LEVEL`
  (deviation: the original silently fixed root level at WARNING)
- Tests skip cleanly when the DB is down (same policy as Phase 2)

## Anti-goals

- NO auth / multi-user (out of scope for the public replica)
- NO real O365 / real ERP integration (simulated channels; real mode in Phase 6 only swaps
  transcription/extraction/re-rank/embeddings to live models — delivery stays simulated)
- NO embeddings generation (Phase 4) — demo search relies on the precomputed store + trigram
- NO frontend (Phase 5)
- NO "improvements" to the ported CTE SQL functions or to the search/ranking semantics
