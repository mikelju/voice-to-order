# Deviation 5.1: bilingual UI chrome (ES/EN language switcher)

> Phase 5 extension, implemented in commit `1dfb4d7` (2026-06-19) and documented
> retroactively on 2026-08-31 (the code shipped before this note — recorded as a process
> deviation from the SDD flow: `/5-plan` should have preceded `/6-implement`).

## Context

Phase 5 was closed (SPA ported, demo flow clickable) and Phase 7 had already made the repo
public-ready. The last remaining friction was linguistic, not functional: the whole reason
the repo exists is to be *read* by recruiters and technical reviewers, and the UI they see
first was Spanish-only.

## Problem

The repo language is English (`CLAUDE.md`), but the ported SPA renders its chrome in Spanish
because the original serves Spanish field technicians. Two constraints collide:

- A reviewer who does not read Spanish cannot navigate the multi-step flow — the very
  human-in-the-loop step that defines the product.
- The **data** must stay Spanish and verbatim: the dictated text and the catalog
  descriptions *are* the matching problem this project demonstrates (`data/README.md`).
  Translating them would destroy the evidence.

So the split has to be drawn precisely: chrome is translatable, data is not.

## Root cause

Phase 5 ported the original SPA as-is, strings included — correct as a port (US-4: "no
redesign"), but the replica has a different audience than the production system it copies.
Neither `5.spec.md` nor the master plan anticipated the language of the UI as a requirement.

## Adopted solution

`src/frontend/src/i18n.tsx` — **no new dependency** (anti-pattern guard: the phase forbade
new state/i18n libraries):

- React Context + `useI18n()` hook exposing `t(key, vars?)`, plus a `LanguageSwitcher`
  rendered as an `ES|EN` toggle in the header.
- Flat dictionary, **108 keys in each language** across 13 sections (header/shell, shared
  field labels, input step, demo picker, uploader/recorder, review screen, candidate table,
  dropdown, catalog modal, finalize form, summary, status lights, PDF modal, footer).
- Initial language detected from `navigator.language` (`es*` -> ES, anything else -> EN),
  the choice persisted in `localStorage` under `vto_lang`, with a `try/catch` so a blocked
  storage never breaks rendering.
- `App.tsx` and all 10 flow components consume `t()`. Dates are localized per active language.

**Deliberately NOT translated** (data and contract, not chrome):

- catalog descriptions, dictated transcriptions and article text returned by the backend;
- the accented backend field-name contract (`CANTIDAD` / `ARTÍCULO` / `DESCRIPCIÓN`,
  `items_for_history`) — renaming those would break the ported API contract.

## Impact

- 13 files changed (+532 / -143): `i18n.tsx` (new, 376 lines), `App.tsx`, `main.tsx` and the
  10 flow components.
- No backend change; no new dependency; no API contract change.
- Verification, as in 5.0: the frontend has no test framework (accepted debt), so coverage is
  `tsc -b && vite build` clean (0 type errors) plus a manual smoke of the full demo flow.
- **Debt closed (2026-08-31):** `tests/frontend/test_i18n_parity.py` now enforces what was
  hand-checked — identical key sets in both dictionaries, no empty translations, matching
  `{placeholder}` sets, and every `t('...')` literal used by a component present in the
  dictionary. It parses `i18n.tsx` as text, so the guarantee costs no JS toolchain.
